# マイルストーン3: リライト・地域振り分け・重複検出のプロンプト設計

マイルストーン2（[PROTOTYPE_EXTRACTION.md](./PROTOTYPE_EXTRACTION.md)）で作った `extract_page` / `assemble_articles` の続き。3つのプロンプトを追加した：

- [tag-region.ts](../src/lib/ai/prompts/tag-region.ts) — 地域タグ付け（`tag_region`）
- [rewrite.ts](../src/lib/ai/prompts/rewrite.ts) — 一般公開向けリライト（`rewrite`）
- [detect-duplicates.ts](../src/lib/ai/prompts/detect-duplicates.ts) — 重複・類似検出（`detect_duplicates`）

フルパイプラインを1本で試せるスクリプトも用意した: [scripts/prototype-pipeline.ts](../scripts/prototype-pipeline.ts)（`extract_page → assemble_articles → tag_region → rewrite → detect_duplicates` を一括実行）。

### 見つかった問題と修正: not_suitable_internal_only の過検知

初回実行で、`20260509がんばるニュース.pdf` の2ページ目（国保税・特養待機・ゴミ袋無償化・PFOS地下水調査・公共交通拡充など、市政に対する具体的な政策要望のかたまり）が、丸ごと `not_suitable_internal_only` と判定された。理由を見ると「党市議団３人の当選が必要である」という**選挙運動の一般的な言い回し**と、masthead の「部内資料」表記だけで内部限定と判定していた。

これは要件の意図（内部限定の具体的数値・指示を除外する）よりも過度に保守的で、政党が自サイトで政策・候補者を公表するという通常の広報活動まで塞いでしまう。[assemble-articles.ts](../src/lib/ai/prompts/assemble-articles.ts) の判定基準を修正した：

- masthead の「部内資料」表記は**単独では根拠にしない**（ほぼ全号に付いているため）
- 「◯人の当選をめざす」等の選挙運動の一般的な呼びかけは、それ自体では not_suitable の理由にしない
- 内部限定の**具体的な数値・氏名・指示**が実際にあるかどうかだけを基準にする

修正後に再実行したところ、同じ記事が `rewrite_candidate` に変わり、リライト結果も国保税・教育費無償化・公共交通・PFOS対策等の政策内容を保ったまま、「党市議団３人の当選が必要である」という内部的な目標設定だけを自然に除外できていることを確認した。`134人`（特養待機者数）についても「出典不明のため安全側に倒して数値を伏せた」という、狙い通り慎重な判断がされていた。

### わかったこと・要相談: 重複検出の感度

`推進ニュース2026.07.27.pdf`「7.25西東京トークライブ」記事を、テスト用に用意した過去記事フィクスチャ（同じ3候補者による1ヶ月前の演説会記事）と比較させたところ、`recycled_appeal`（類似度0.85）として実際にフラグが立った。

これは意図的な設計判断が必要な点だと考えている。今回の新記事には「200人参加」「ペンライトライブ」など新しい具体的事実が含まれており、私の当初の想定（新しい事実があれば重複ではない）ではフラグを立てないはずだったが、AIは「同じ3候補者による同種の演説会が短期間に複数回報告されている」こと自体を recycled_appeal のパターンとして扱った。

自動ブロックはしない設計なので実害は「レビュー画面に一つ警告バッジが出る／担当者が1クリックで却下する」程度だが、選挙運動期間中に同じ候補者の活動を継続的に報告する記事すべてに警告が出るのは煩わしい可能性もある。

**→ ユーザー判断: 「内容が実質的に同じ場合のみ警告を出す」を採用。** [detect-duplicates.ts](../src/lib/ai/prompts/detect-duplicates.ts) を修正し、「同じ候補者・同じテーマ・同種のイベント」というだけでは flag しない、新しい具体的事実（日時・参加人数・発言内容等）を伴う報告は flag しない、迷ったら flag しない方向に倒す、という基準を明記した。同じフィクスチャで再実行し、重複フラグが0件になることを確認済み。

## tag_region の設計

- `source_type = 'ganbaru_news'` の記事は常に `region_tag = 'kodaira'` に固定し、**AIを呼ばない**（小平市委員会発行のため判定不要。コスト削減にもなる）
- `source_type = 'suishin_news'` の記事のみプロンプトを呼ぶ。まずベースの地域タグ（`kitatama_tobu` / `multiple`）を決め、別途「西東京特化の派生記事を作るべきか」を判定する2段構成にした（`undetermined` は後のフィードバックで廃止。下記changelog参照）
- 実サンプル（`推進ニュース2026.07.27.pdf`「7.25西東京トークライブ」記事）で検証：西東京市議選予定候補3人の紹介・西東京市内での演説会報告は、`base_region_tag: kitatama_tobu`（地区全体の活動報告として）かつ `nishitokyo_derivative_recommended: true`（西東京HP向けにも展開すべき）という、狙い通りの判定になることを確認した（手作業での参考例による検証。実際のAPI出力は未検証）

## rewrite の設計

- `public_suitability = 'not_suitable_internal_only'` の記事にはこのジョブを自動実行しない（[DATA_MODEL.md](./DATA_MODEL.md) 参照）
- 出力に `internal_info_flags` を含め、リライト後の本文に内部限定情報が残っていないかの安全弁チェックを兼ねさせた。各フラグに `present_in_rewrite`（リライト後にまだ残っているか）を持たせ、UIでは「未確認（要対応）」と「除外済み（参考表示）」を分けて見せる設計（マイルストーン1のモックアップの記事編集画面に対応）
- カテゴリに `personal_privacy` を追加した。実サンプル（`推進ニュース2026.07.27.pdf`「柳沢・東伏見支部で真ん中世代が入党」）に、新規入党者個人を年代・家族との会話まで含めて紹介する記事があった。政党の党員であることは個人情報保護法上の要配慮個人情報にあたり、本人の同意なく公開すべきでないため、このケースは記事全体を `not_suitable_internal_only`（`personal_privacy`理由）とし、リライト自体を行わない設計にした

## detect_duplicates の設計

- 全過去記事との総当たりは非効率なため、候補の絞り込み（同じ地域タグ・直近数ヶ月等）はアプリケーション側で行い、プロンプトには絞り込み済みの候補一覧だけを渡す
- `duplicate_content`（ほぼ同一内容の二重掲載）と `recycled_appeal`（同じ趣旨の呼びかけの短期間の繰り返し。要件にある選挙前後の「檄」パターン）を区別
- **わかったこと**: 実サンプルの「西東京トークライブ」記事を、類似する過去のフィクスチャ記事（同じ3候補の必勝演説会、1ヶ月前）と比較する参考例を作ったところ、正しい挙動は「フラグを立てない」だと判断した。理由は、両記事とも開催日・参加人数・会場の様子など**新しい具体的事実**を報告しており、要件が問題視している「中身のない同じ訴えの繰り返し」には当たらないため。これは重要な設計上の注意点で、プロンプトが単に「同じ候補者名・同じイベント種別」というだけで過検知しないよう、「新しい情報の有無」を判断基準に明記した
- ただし実サンプルには `recycled_appeal` が正しく発火する陽性ケースが無かった。実際のAPI疎通確認ができ次第、意図的に「中身のない繰り返し」を含む合成テストケースで陽性側の検証を行う必要がある

## 次のマイルストーンへの引き継ぎ

- 5つのプロンプト（extract_page / assemble_articles / tag_region / rewrite / detect_duplicates）を実サンプル3件・実際のAPI出力で検証済み。1件の過検知バグを発見・修正・再検証済み
- 重複検出の感度についてはユーザーの意見待ち（上記参照）。運用しながら調整する前提でもよい
- マイルストーン4（ダッシュボードUIの実装：マイルストーン1のモックアップをNext.jsで実データと接続する）に進める状態

## マイルストーン4後のフィードバック対応（changelog）

ダッシュボードを実際に触ってもらった上でのフィードバックに基づく変更点。

- **JSON解析エラーの根本修正**：テキスト応答からJSONを正規表現で抜き出す方式は、長い本文で無効なJSONを生成することがあった（実例:「推進ニュース2025.10.21.pdf」で構文エラー）。Claude の Tool Use（Structured Outputs）に切り替え、5つのプロンプトすべてでAPIレベルの有効なJSON保証に変更（[run.ts](../src/lib/pipeline/run.ts)）
- **rewrite プロンプトの全面書き直し**：内部限定情報を削ることに寄りすぎ、ペンライト演出等の党の工夫の描写までごっそり削ってしまう問題があった。「削ってよいもの（内部限定の数値・指示・個人情報）」と「残すべきもの（政権・市政批判、党の奮闘・工夫）」を明確に線引きし、公式サイトの目的を「情勢認識と党の奮闘を伝えること」に据え直した（[rewrite.ts](../src/lib/ai/prompts/rewrite.ts)）
- **党内用語辞典を追加**：青本・赤本・緑本・○中総等の頻出党内用語を、単に削除するのではなく「用語（説明）」の形で解説を添えるようにした。カテゴリ・用語ともに `/glossary` 画面から追加できる。同一記事内の2回目以降は説明を省略、「○」は本文中の実際の数字に置き換える（[rewrite.ts](../src/lib/ai/prompts/rewrite.ts) の党内用語辞典セクション、[DATA_MODEL.md](./DATA_MODEL.md) の `glossary_categories`/`glossary_terms`）
- **detect_duplicates の感度調整**：「同じ候補者・同じテーマというだけでは flag しない」を明記（上記参照）
- **tag_region から `undetermined` を廃止**：国政・都全体の会議等、どの市にも紐づかない話題で「判定不能」が多発した。ユーザー指示により、該当する場合は `kitatama_tobu` をデフォルトにするようスキーマ自体から `undetermined` を削除した（[tag-region.ts](../src/lib/ai/prompts/tag-region.ts)）。内容の公開可否の疑問は地域タグではなく `public_suitability` が担うため、責務の重複もこれで解消された
